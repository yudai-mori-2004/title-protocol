## Round 2 で新たに発見した問題

### round2-N1 (must-fix) §1.2 表中 measurement の説明と §6.2 確認 2 の説明が PCR の扱いで食い違っている

- 場所: `docs/v0.1.2/SPECS_JA.md:149` と `:1218`
- 観察:
  - L149: "AWS Nitro では PCR0（enclave image、48 バイト SHA-384）が主要な照合対象だが、より厳格な検証では PCR1（カーネル/initrd）や PCR2（アプリケーション）も合わせて比較できる"
  - L1218: "measurement は TEE バイナリのビルド結果から決まる固定値であり、ベンダー…によって長さや算出方法が異なる（AWS Nitro は 48 バイトの SHA-384）"
- 問題: §1.2 で "PCR0 / PCR1 / PCR2 の組として扱える" と幅を持たせたが、§6.2 確認 2 では再び "AWS Nitro は 48 バイトの SHA-384" と単一値で書かれている。Solana プログラムの実装者は §6.2 だけ読んで「measurement = PCR0 単一の 48 バイト」を前提に PDA を設計してしまう。Round 1 must-004 への修正が §1.2 だけで止まり、§6.2 に伝播していない。
- 攻撃者視点: §6.2 だけが Source of Truth として実装されると、攻撃者は同一 PCR0（= 同じ enclave image）の下で別の initrd / アプリケーションを読み込んだ enclave を立て、measurement 照合を通せる余地が残る。Round 1 must-004 の攻撃面が §6.2 経由で復活している。
- 修正案: §6.2 確認 2 (L1218) の括弧を "(AWS Nitro では PCR0/PCR1/PCR2 の組を measurement として扱う。長さや算出方法はベンダーごとに異なる)" に書き直す。または "measurement の定義は §1.2 を参照" の一文を加え、二度書きを避ける。

### round2-N2 (must-fix) §6.2 確認 1 の "管理者" と §1.6 「コア処理に限る」 注記との関係が不明

- 場所: `docs/v0.1.2/SPECS_JA.md:310` と `:1208`、`:1216`
- 観察:
  - L310: "Extension（§6）は追加の信頼前提を持つ場合がある（例: Solana Extension は whitelist 管理者を信頼前提に加える）"
  - L1208: "verifying_key_hash …集合の更新権限は管理者のみが持つ"
  - L1216: "measurement の集合…別途オンチェーンに保持する…Title Protocol の正規 TEE バイナリの measurement だけが集合に登録されている"
- 問題: §1.6 の括弧は "whitelist 管理者" を 1 箇所しか挙げていないが、実態としては (a) whitelist PDA の管理者、(b) verifying_key_hash 集合の管理者、(c) measurement 集合の管理者、(d) revoke 権限保持者（§6.2 末尾）が出てくる。これらが同一主体か別主体か、複数署名なのか単独鍵なのかが書かれていない。攻撃者視点では、この "管理者" の鍵が漏れたときの被害範囲（measurement 集合に偽値を追加できる = 攻撃者の自前 TEE を正規化できる）が決定的な情報だが、現状無記述。
- 修正案: §6.2 冒頭または "集合の運用" 節に「3 つの管理者ロール（whitelist / verifying_key_hash 集合 / measurement 集合）は同一の管理鍵で運用するか分離するかをここで規定する」と明示。最低限「全集合の更新権限を持つ管理鍵を信頼前提に加える」と §1.6 の括弧書きを拡張する。

### round2-N4 (should-fix) §1.7 の "改変は以下のいずれかで検知される" 後の bullet が網羅性で破綻

- 場所: `docs/v0.1.2/SPECS_JA.md:321-326`
- 観察:
  - L321: "改変は以下のいずれかで検知される"
  - L323: 処理結果の改変 → user_data 照合で検知
  - L324-326: リクエスト内容の改変 → 利用形態別、サーバーサイドは「対象外」、クライアントサイドは「TEE 内検知不能、クライアント側照合のみ」
- 問題: "いずれかで検知される" と宣言したのに、サーバーサイド利用での改変は "対象外" と書かれている。攻撃者視点では「サーバーサイド利用で Gateway が悪意化したケースは未防御」と読める。実装者視点では、サーバーサイド利用と銘打って Gateway を別運営者に委託している運用が存在し得る（例: マネージドホスティング）ため、"クライアントと Gateway は同一運営者" を前提化するのは現実とずれる。
- 修正案:
  - "サーバーサイド利用" の前提条件（「クライアントと Gateway を同一運営者が運用する場合のみ非暗号化を選択可」）を §1.4 または §2.4 の冒頭で正式な制約として明記する。
  - §1.7 の bullet は "防御外" ではなく "クライアント側で signature_hash を事前計算しレスポンスと突合する手順は非暗号化モードでも適用可" と書く。signature_hash はレスポンスに含まれるため、暗号化の有無を問わずこの突合は可能なはず。

### round2-N5 (should-fix) §1.6 と §2.4 の "ストレージ運営者の信頼" 扱いがずれている

- 場所: `docs/v0.1.2/SPECS_JA.md:308`, `:547`
- 観察:
  - L308: "プロトコルの運営者、Gateway、ストレージの提供者、その他いかなる主体への信頼も不要である"
  - L547: "ストレージの運営者と Gateway は、リクエスト（ペイロード）もレスポンス（処理結果）も読めない"
- 問題: L308 が "ストレージ提供者への信頼は不要" と断じているが、L547 はその根拠を「ペイロードを暗号化しているから読めない」に限定している。暗号化モードを選択しない場合、ストレージは平文コンテンツを読める = 完全に "信頼が不要" ではない。秘匿性に関しては明らかに信頼が必要。L308 を文字通り読むと「ストレージは秘匿性も保証してくれなくてよい」と取れて、利用者の判断を誤らせる。
- 修正案: L308 を「処理結果の完全性についてはストレージ等を含むいかなる主体への信頼も不要である。コンテンツの秘匿性が必要な場合は §1.4 の暗号化オプションを用いる」と完全性／秘匿性で書き分ける。

### round2-N6 (should-fix) §6.2 確認 2 末尾「TEE バイナリを変更したときのみ新しい measurement を追加」は再起動と矛盾しうる

- 場所: `docs/v0.1.2/SPECS_JA.md:1218`
- 観察: "TEE バイナリを変更したときのみ、新しい measurement を集合に追加する"
- 問題: §5.2 起動シーケンス（L1041）と §6.2 運用（L1325-1327）では「TEE 再起動が頻繁に起こる」前提だが、measurement は再起動で変化しない（同じバイナリのため）はず — ただし、PCR1（カーネル/initrd）まで含めると、ホスト OS のカーネル更新で値が変わり得る。round2-N1 の "PCR の組" 議論と接続すると、measurement 集合の更新頻度は「TEE バイナリの変更時のみ」ではなく「PCR の構成要素のいずれかが変わったとき」に拡張される。
- 修正案: round2-N1 とまとめて修正する。"measurement の更新トリガーは PCR0/PCR1/PCR2 のいずれかが変化する操作（enclave image / カーネル・initrd / アプリケーションの再ビルド）であり、その都度ホワイトリストに新値を追加する" と明示する。

### round2-N7 (should-fix) §2.4 ステップ 8 のエラー時挙動と Round 1 修正 (must-009) の表現が逆向き

- 場所: `docs/v0.1.2/SPECS_JA.md:489-490`, `:326`
- 観察:
  - L489-490: "ペイロード内の signature_hash と算出値が一致するか検証する → 不一致ならエラー（ペイロード内部の改ざん検知）"
  - L326: "Gateway が content_url を別ペイロードに差し替えた攻撃は TEE 内では検知不能"
- 問題: ステップ 8 では「TEE 内で signature_hash 一致確認 → 不一致ならエラー」が走るのに、L326 (Round 1 で must-009 の修正として加筆された箇所) では「TEE 内では検知不能」と断じている。両者は別の攻撃モデルを語っているため厳密には矛盾しないが、初見の実装者には矛盾に見える。具体的には:
  - ステップ 8 は「TEE が読んだコンテンツ」と「クライアントが宣言した signature_hash」の一致を見ている → クライアントが嘘の signature_hash を入れれば検知
  - L326 は「攻撃者がコンテンツも signature_hash もまるごと差し替えた整合的なペイロード」を想定 → ステップ 8 では検知できない
- 修正案: L326 の表現を「Gateway が暗号化ペイロード全体（content_url が指す先のバイナリ）を、攻撃者が事前に正規 TEE 公開鍵で暗号化した別ペイロードに差し替える攻撃は、内部で signature_hash 一致が成立するため TEE 内では検知不能」と限定する。ステップ 8 の役割（クライアントの宣言と実コンテンツの整合確認）も同等の明示を加える。

### round2-N8 (should-fix) §5.2 自己 Attestation 取得失敗時の "起動を中止する" が他のエラー処理規範と粒度がずれている

- 場所: `docs/v0.1.2/SPECS_JA.md:1043-1045`
- 観察: "自己 Attestation の取得に失敗した場合、TEE は起動を中止する。measurement を保持できない状態でリクエスト受付を開始すると、後続の処理で measurement 一致確認が事実上スキップされ、信頼モデルが崩壊するためである。"
- 問題: 全仕様書中、「失敗したらどうする」が明文化されている箇所がここくらいしかない。他の失敗ケース（鍵ペア生成失敗、Gateway への公開鍵通知失敗、復号失敗以外のリクエスト処理エラー）の挙動がフラットに書かれていない。一方でここだけ "起動を中止する" と強い規範を書くと、他の節を読む実装者は「明示されていない失敗は継続して良い」と誤解する余地ができる。
- 修正案: 失敗時の挙動を統一的にまとめる節（例: §5.2 末尾「起動・運転時のエラーハンドリング規範」）を起こし、(1) 起動時 fatal、(2) リクエスト処理時のエラー応答、(3) Attestation 取得失敗時の挙動 を表で並べる。

## 全体所感
