### must-fix-001 `signer` フィールドの型がレスポンス例と processor 出力定義で矛盾

- 場所: `docs/v0.1.2/SPECS_JA.md:441` と `docs/v0.1.2/SPECS_JA.md:734-737`
- 観察:
  - §2.3 レスポンス例 (L441): `"signer": "Google"` — 単純な文字列
  - §3.2 c2pa-verify 出力例 (L734-737): `"signer": { "issuer": "Google LLC", "cert_serial": "..." }` — オブジェクト
- 問題: 同一フィールド名が同一仕様書内で「文字列」と「オブジェクト」の 2 つの型として例示されている。実装者は §2.3 を見れば文字列で実装し、§3.2 を見ればオブジェクトで実装する。検証者の照合 (JCS 正規化前提) では完全一致が必要であり、型不一致はそのまま検証不能を意味する。
- 修正案: §2.3 のレスポンス例を §3.2 と一致させる。`"signer": { "issuer": "Google LLC", "cert_serial": "..." }` で統一し、§2.3 の例文をそのまま差し替える。あわせて「processor 個別の出力構造はセクション 3 を Source of Truth とする」と §2.3 末尾に一文追加する。

### must-fix-002 `salt=encap_key` の HKDF はレスポンス側で encap_key を運ばないと検証者が再現できない

- 場所: `docs/v0.1.2/SPECS_JA.md:496-497` と `docs/v0.1.2/SPECS_JA.md:507-515`
- 観察:
  - L496-497: `request_key = HKDF-SHA256(shared_secret, info=..., salt=encap_key)` `response_key = HKDF-SHA256(shared_secret, info=..., salt=encap_key)`
  - L507-515: レスポンスのワイヤーフォーマットは `nonce | ciphertext` のみ。「クライアントは同一の KEM 交換から導出した response_key を既に保持しているため」と説明
- 問題: クライアントが暗号化リクエストを送ったセッション内で復号する分には成立する。しかし「暗号化リクエストとレスポンスは別 HTTP/接続でも構わないか」「クライアントが再起動した後にレスポンスだけを後から取得するシナリオはあり得るか」が一切記述されていない。実装者が「リクエスト/レスポンスは同一 TCP 接続必須」と推測するか「永続化可能」と推測するかでアーキテクチャが分岐する。また `salt=encap_key` を採用した目的 (transcript binding 等) も書かれていない。
- 修正案:
  - 「リクエストと対応するレスポンスは同一クライアントセッション内でのみ復号可能。暗号化セッションの永続化はサポートしない」と §2.4 に明示。
  - `salt=encap_key` の意図 (例: 同一 TEE 鍵を再利用する複数セッションで HKDF 出力を区別する transcript binding) を 1 文で説明。意図が不要なら `salt=None` でよい。

### must-fix-003 §6.2 内の「二段の照合 / 三つの確認」が矛盾している

- 場所: `docs/v0.1.2/SPECS_JA.md:1177`, `:1183`, `:1187`, `:1207-1209`
- 観察:
  - L1177: 「プログラムが二段の照合を実施」
  - L1183: 「後述する三つの確認をすべて通過した ZK proof でのみ」
  - L1187: 見出し「二段の同一性確認」
  - L1191/1199/1207: 本文では「確認 1 / 確認 2 / 確認 3」と 3 つ列挙
- 問題: 「二段」と「三つ」が同じ仕様書内で混在。見出しは「二段」だが本文は「3 つ」。読み手はどちらが正しい設計か判断できない。Solana プログラム実装者がこの節だけ見て命令を書くと、確認 3 を実装し損ねる可能性が高い。
- 修正案: 全箇所「三つの確認」「三段の同一性確認」に統一する。確認 1 (verifying_key_hash)、確認 2 (measurement)、確認 3 (鍵と Attestation の bind) は本質的に並列の 3 チェックであるため、構造的にも 3 で揃える方が自然。L1177 の流れ図も「三段の照合」に修正。

### must-fix-004 AWS Nitro の measurement を「PCR0 のみ」と断じている

- 場所: `docs/v0.1.2/SPECS_JA.md:149`, `:1205`
- 観察: 「AWS Nitro では PCR0 と呼ばれる 48 バイトの SHA-384 ハッシュ」「AWS Nitro は 48 バイトの SHA-384」
- 問題: AWS Nitro Enclaves の Attestation Document は PCR0 (enclave image)、PCR1 (linux kernel + bootstrap)、PCR2 (application)、PCR8 (image signing certificate) を含む。実運用ではこれら複数の PCR を照合するのが標準。Spec が「PCR0 のみ」と読める書き方をしていると、検証者実装が PCR1/PCR2 を無視する弱い検証になる。攻撃者は同一 PCR0 で別の OS/initrd を読み込んだ enclave を立てる経路で偽造を試みる余地が生まれる。
- 修正案:
  - 「AWS Nitro では PCR0〜PCR2 (および署名済み起動時の PCR8) の組を measurement として扱う」と修正。
  - 検証回路 (§6.2 確認 2) でどの PCR を照合するか明示する。`(PCR0, PCR1, PCR2)` の三組などタプル単位での照合を推奨。

### must-fix-005 ETag/If-Match による「異バージョン混在防止」の理屈が C2PA Merkle 検証の機能と重複/誤誘導

- 場所: `docs/v0.1.2/SPECS_JA.md:1087`
- 観察: 「Range Request を用いる場合、初回リクエストで取得した ETag を以降のリクエストの If-Match ヘッダに含める。取得の途中でストレージ上のファイルが変更された場合、412 Precondition Failed が返され、処理を中断する。これにより、異なるバージョンのファイルからチャンクを混在して読み取ることを防ぐ。」
- 問題:
  1. 仕様書本文では「Merkle tree ベースのチャンク検証」(L899, L1085) が異バージョン混在を暗号学的に検知できると主張している。If-Match による HTTP レイヤーの保護はストレージサーバを信頼する前提に依存し、TEE モデルの「外部主体への信頼を不要にする」原則に整合しない。
  2. すべてのオブジェクトストレージが ETag/If-Match を返すとは限らない (S3 は OK だが任意のユーザー指定ストレージは未保証)。「Range Request 非対応の場合」の代替は書いてあるが「If-Match 非対応の場合」の挙動が未定義。
  3. C2PA の hash binding が破れる前提で If-Match に依存しているのか、二重防御なのかが書かれていない。
- 修正案: 「If-Match は性能上のフェイルファスト目的の defense-in-depth であり、整合性の根拠は C2PA の Merkle 検証 (および TEE 内ハッシュ照合) である。If-Match が利用できないストレージでは省略可」と明示する。または、本当にプロトコル上必須なら「If-Match 非対応ストレージは未サポート」と明記する。

### must-fix-006 `signature_hash` の定義が C2PA の構造から見て曖昧

- 場所: `docs/v0.1.2/SPECS_JA.md:195`, `:455`
- 観察: 「コンテンツの Active Manifest (最新のマニフェスト) の署名の SHA-256 ハッシュ」
- 問題:
  - C2PA の署名は COSE_Sign1 構造 (CBOR エンコード) であり「署名」と一口に言っても (a) `signature` バイト列、(b) `to_be_signed` バイト列、(c) COSE_Sign1 全体、(d) JUMBF box 全体、で取りうるバイト範囲が異なる。
  - 「同一の C2PA コンテンツからは、誰が計算しても同一の signature_hash が得られる」と主張しているが、上記の範囲が不定だと計算結果が分岐する。
  - 「Active Manifest」自体の選択基準 (JUMBF 内の active claim 指定？) も C2PA 仕様に明確な参照が必要。
- 修正案: signature_hash = SHA-256( <具体的なバイト範囲> ) を c2pa-rs のどの API/フィールドに対応するかを明記。例: 「Active Manifest の COSE_Sign1 構造体の `signature` フィールド (raw byte string) に対する SHA-256」+「Active Manifest の決定は C2PA 2.x §X.Y に従う」。

### must-fix-007 Solana Extension の「有効/無効」がどう決まるかが未定義

- 場所: `docs/v0.1.2/SPECS_JA.md:660`, `:678`

### must-fix-008 「Gateway は内容を改変できない」と「Gateway は content_url を差し替え可能」が同居している

- 場所: `docs/v0.1.2/SPECS_JA.md:317`, `:319-322`, `:348`, `:632`
- 観察:
  - L317: 「Gateway はプロトコルの信頼モデルには関与しない。処理結果を改ざんすることはできない」
  - L319: 「Gateway はリクエスト内容 (content_url、processor_ids 等) を改変する能力を物理的に持つ」
  - L348: 「Gateway はリクエストをそのままにするか拒否するかだけであり、内容の改変はできない」
  - L632: 「Gateway はリクエストとレスポンスをそのまま中継する。内容の改変は行わない」
- 問題: L319 だけが「物理的に持つ」と認め、他の 3 箇所は「改変できない」と断定している。これは「能力としてはある」「ポリシーとしてしない」の区別が曖昧。攻撃者視点ではこの区別こそが信頼モデルの根幹であり、ここを誤読すると「Gateway を信頼してよい」と誤って実装される。
- 修正案: L317/L348/L632 を「Gateway は信頼されない構成要素であり、改変能力は持つが、改変は signature_hash 照合 (§1.7/§2.4 ステップ 12) で検知される」と書き直す。「改変できない」という断定表現を全箇所で禁止する。

### must-fix-009 §2.4 ステップ 12 と §1.7 「クライアントサイド利用」の防御範囲が不一致

- 場所: `docs/v0.1.2/SPECS_JA.md:322`, `:541`
- 観察:
  - §1.7: 「Gateway が content_url を差し替えた場合、返却される signature_hash が変わるため、クライアントがレスポンスの signature_hash をローカルで算出した値と照合することで攻撃を検知できる」
  - §2.4: 「Gateway が content_url を別のペイロードに差し替える攻撃は、TEE 内部では検知できない (攻撃者のペイロード内部の signature_hash とコンテンツは整合するため)」
- 問題: §2.4 では「TEE 内部で検知不能、クライアント側照合のみが防御」と明示しているが、§1.7 では「signature_hash が変わるから検知できる」とだけ書き、TEE 内検知できないことが書かれていない。§1.7 だけ読んだ実装者は TEE 内検知に依存した設計を組む。
- 修正案: §1.7 のくだりを「TEE 内部では検知不能であり、クライアントが事前計算した signature_hash とレスポンスを比較することでのみ検知される」と明示。§2.4 ステップ 12 と同じ表現で揃える。

### should-fix-008 §4.3 サイドカーのメモリパターン記述が薄い

- 観察: 「サイドカー: マニフェストとコンテンツを個別にダウンロードし、処理する。メモリパターンは単一ファイルとほぼ同じで、マニフェスト分 (数 KB〜数十 KB) が追加される。」3 文のみ。
- 問題: 単一ファイルと違い「2 つの URL を取得する」ため、(a) 取得順序 (マニフェスト先 → コンテンツ後 か並列か)、(b) どちらかが失敗した場合の挙動、(c) コンテンツの大きさ次第で Range Request を使うか、が一切書かれていない。攻撃者にとっては「マニフェストだけ正規物、コンテンツだけ別物」という差し替え攻撃の余地を考える材料になる。
- 修正案: §4.3 サイドカーに「マニフェスト先取得 → コンテンツは Range Request で必要部分のみ取得 → ハードバインディングハッシュで突合」のフローと、突合失敗時の挙動を明記。

### should-fix-009 「TEE は再起動で鍵が変わる」 vs 「Solana 署名鍵は 90 日有効期限」の関係が不明瞭

- 場所: `docs/v0.1.2/SPECS_JA.md:469`, `:1310-1314`
- 観察:
  - L469: 「TEE が再起動すると鍵ペアは失われ、新しい鍵ペアが生成される」(暗号化用)
  - L1310-1314: 「ホワイトリストに登録された署名鍵には、新規発行に対する有効期限 (目安: 90 日) を設ける」「定期的な鍵のローテーションは TEE の再起動 (停止 → 起動) で自然に行われる」
- 問題: TEE が再起動する頻度と 90 日の関係が読み取れない。TEE が 90 日連続稼働する想定なら EC2 上の単一インスタンスを長期稼働させる前提だが、Nitro Enclave は親 EC2 の停止・パッチ・再起動で定期的に死ぬのが現実。90 日経つ前に TEE が死ねば「有効期限」は形骸化し、90 日連続稼働するなら鍵ローテーションは「自然に」起こらない。
- 修正案: 「90 日の有効期限は『鍵が長期に永続化しないことの保証』として設計されており、TEE の自然な再起動サイクル (週次〜月次想定) で実質的に短縮される」を明記。または「TEE は最大 90 日で強制再起動する」運用ポリシーを追加。

### should-fix-010 §6.2 の「ホワイトリスト鍵の取り消し」とコア §1.6「外部信頼不要」の矛盾

- 場所: `docs/v0.1.2/SPECS_JA.md:306`, `:1316-1322`
- 観察:
  - §1.6: 「プロトコルの運営者、Gateway、ストレージの提供者、その他いかなる主体への信頼も不要である」
  - §6.2 運用: 「TEE の侵害等、特別な事情が発生した場合にのみ、管理者が該当する鍵を取り消す」
- 問題: Solana Extension を含めた全体では「管理者の判断 (revoke するかしないか)」への信頼が発生する。§1.6 はコアのみに限った宣言なら明示が必要。
- 修正案: §1.6 に「本節の信頼モデルはコア処理に限る。Extension (§6) は追加の信頼前提を持つ場合がある」と注記。§6.2 冒頭にも「Solana Extension はホワイトリスト管理者を信頼前提に加える」と明示。

### should-fix-011 P-256/X25519 ephemeral public key のエンコーディング規約が未定義

- 場所: `docs/v0.1.2/SPECS_JA.md:570`
- 観察: 「`encap_key` 鍵交換データ (X25519: 32 バイト、P-256: 65 バイト、ML-KEM-768: 1088 バイト)」
- 問題: P-256 = 65 バイトは uncompressed SEC1 (0x04 || X || Y) と推測されるが書いていない。圧縮表現 (33 バイト、0x02/0x03 || X) を実装すると相互運用不能。X25519 32 バイトも big-endian と little-endian の区別が必要 (RFC 7748 は little-endian)。Base64 のエンコード方式 (standard vs URL-safe) も `/keys` レスポンス (L591-593) で未指定。
- 修正案: 「P-256 は SEC1 uncompressed (0x04 prefix, X||Y)、X25519 は RFC 7748 little-endian、ML-KEM-768 は FIPS 203 §7.1 の encapsulation key 形式、Base64 はすべて RFC 4648 §4 (standard, padding あり)」と表に追加。

### should-fix-012 §3.3「Processor の追加」が運用ポリシー寄り過ぎる

- 場所: `docs/v0.1.2/SPECS_JA.md:836-846`
- 観察: 「processor の追加・変更の判断はプロトコルの運営者が行う」
- 問題: ここは技術仕様書なので運営の判断主体は本来オフトピック。代わりに「処理追加時の互換性ルール (既存 processor の出力を変えるとどうなるか)」「processor の deterministic 性要件」など仕様上の制約を書くべき。
- 修正案: 運営者の文を削除し、「processor 追加・変更で TEE measurement が変わる。検証者は古い processor 出力を新しい measurement で再検証することはできない」「processor は decisive かつ deterministic でなければならない (同一入力で常に同一出力)」を追加。

### should-fix-013 §0.1 の C2PA v2.3 (2026 年 1 月) が現行版という記述

- 場所: `docs/v0.1.2/SPECS_JA.md:9`
- 観察: 「v2.3 (2026 年 1 月) が現行安定版である」

## 全体所感

仕様書としての骨格 (信頼モデル、Attestation Document の役割、暗号化のオプション性、Extension の境界) は明確で、v0.1.0 と比べて大幅にスリム化されている点は良い。一方で、本監査で挙げた must-fix の多くは「同じ概念を複数の節で再説明している過程で表現が分岐した」もので (signer の型、二段/三つ、Gateway の改変能力)、章単位で独立に書かれて後で merge した形跡が透けて見える。

最も読み手を惑わせるのは §6.2 で、ZK proof / verifying_key_hash / measurement / user_data bind の 4 概念が連続して登場するため、3 つの確認が「二段」と書かれていたり、PCR0 単一前提のように読めたりする箇所が混入している。Solana Extension は本仕様書の中で最も「正しく実装しないとプロトコル全体の信頼が崩れる」節なので、3 つの確認の構造化と PCR の扱いは早期に整理すべき。

攻撃者視点では must-fix-004 (PCR0 だけだと自前 enclave の余地)、must-fix-008 (Gateway 改変能力の曖昧化)、should-fix-010 (revoke 管理者への暗黙信頼) が最も突かれやすい。
